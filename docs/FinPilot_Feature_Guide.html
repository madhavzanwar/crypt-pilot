1. System overview

One ledger per user, many views of it.

FinPilot is a personal-finance copilot. Everything revolves around one ledger per user (accounts, transactions, budgets, goals). The web app, the phone app and every analysis read and write that same ledger, which is why a payment made on the phone shows up on the dashboard within about a second.

Figure 1. Components and how they talk. Solid arrows are requests; dashed arrows are identity or fallback.

The three rules the design follows

  • Numbers are computed, not generated. Forecasts, risk, simulators and the payment check are deterministic code over your data. LLMs are used only for language and vision (naming a photographed item, answering chat), never to produce a financial figure.
  • Private data stays local first. OCR and image embeddings run on the machine (ONNX on CPU). Statements are redacted before anything is previewed or stored. Hosted models are optional fallbacks.
  • One source of truth. There is a single backend store module. Every router goes through it, so caching, invalidation and the live-sync counter are consistent.

Request path of a typical page

StepWhat happens
1Browser holds a Firebase ID token (or a demo/guest id). apiFetch adds it as Authorization: Bearer.
2FastAPI dependency resolve_user_id checks the token's subject equals the {user_id} in the URL. Demo personas and guest sandboxes are public fixtures and need no token.
3Router reads rows through store.query (cache, then Firestore) and computes the answer with pandas/numpy.
4Response is a Pydantic model, so the frontend types in lib/types.ts mirror it.
5LiveSync polls a change counter; when it moves, the API cache is cleared and every mounted page refetches.

Feature 1

Opt-out expense simulator

See what you would save, per year and in a 12% SIP, if you cancel everyday subscriptions and habits.

What it does

A tab on /simulate. You list recurring spends (Spotify, Netflix, Hotstar, doodhwala, newspaper, gym, broadband and your own). A toggle cancels each one, and the page shows monthly saving, new savings rate, yearly saving and the future value if the saved money went into a SIP.

How it works

  • Each item has cost (today) and replacement (what you would still spend, e.g. packet milk instead of a doodhwala). Saving = cost - replacement for cancelled items.
  • Before: savings = income - other - sum(cost). After: savings + saving. Savings rate = savings / income.
  • 12-month future value of the monthly saving uses the annuity-due formula with SIP_RATE = 12% p.a.: FV = P * ((1+r)^n - 1) / r * (1+r), r = 12%/12.
  • Subscriptions detected in your real data (the dashboard's recurring obligations of category subscriptions) are offered as one-click additions, normalised to a monthly amount by frequency (weekly 52/12, quarterly 1/3, annual 1/12).
FormulaValue
Monthly savingsum over cancelled (cost - replacement)
Future valueP x ((1+r)^12 - 1)/r x (1+r), r = 0.01
Savings rate(income - other - spend) / income

Data and stack

Datayour inputs + detected subscriptions from /api/dashboard
StackReact state + useMemo, Recharts area chart, Framer Motion
Why client-sideinstant feedback while toggling; no server round trip for pure arithmetic
No LLMall arithmetic

Limits

The 12% return is illustrative, not a promise, and is labelled as such. Items you add are not saved between sessions.

Feature 2

Phone OTP for the Google Pay link

Prove you own the mobile number before linking a UPI source.

What it does

In Connect > Google Pay, after choosing a demo profile and entering a mobile number, the dialog sends a real SMS one-time code through Firebase Phone Auth and asks for it before the Account Aggregator consent step proceeds.

How it works

  • The OTP uses a separate Firebase app instance named phone-verify with in-memory persistence. Verifying a number therefore never signs the user in as that number or changes who the app thinks the user is.
  • A new RecaptchaVerifier is created for every attempt and cleared after failure or success, because a verifier cannot be reused.
  • Numbers are normalised to +91 and validated as 10 digits before any SMS is sent.

Data and stack

ProviderFirebase Authentication, Phone provider
Clientlib/firebase/auth.ts: sendPhoneOtp, confirmPhoneOtp
UILinkGooglePayDialog phases: details, verify, otp, working
Why FirebaseSMS delivery, rate limiting and abuse protection are hard to do safely ourselves

Limits

Needs the Phone provider enabled in the Firebase console and an authorised domain (localhost is allowed). Real SMS costs apply beyond the free tier; test numbers can be configured in Firebase.

Feature 3

Forecast & Risk

A probabilistic cash-flow forecast, the chance you run short, four scenarios side by side, and proof of how accurate it has been.

What it does

The /forecast-risk page has four tabs: Forecast (P10-P90 fan of income, essentials, discretionary and net cash), Risk (probability of falling below a safety reserve each month, severity, drivers), Scenarios (do nothing vs cut discretionary vs extra debt payment vs extra saving, on the same simulated futures) and Accuracy (backtest versus baselines and calibration of the risk numbers).

Pipeline

Figure 2. One request builds the whole report. Everything after the history is a pure function: same inputs and seed give identical output.

The forecaster (<code>plan/forecast.py</code>)

  • Streams. Three monthly series: income, essential spend, discretionary spend.
  • Point forecast. Median of the last W months per stream. W is chosen from (3, 6, 12, 24) by one-step-ahead rolling-origin error of net cash on a validation block that sits before the test months. The longest window wins unless a shorter one beats it by more than 5%, because the validation block is short and noisy.
  • Uncertainty. The residual vector of a whole month (all three streams together) is resampled with replacement. Resampling jointly keeps correlation: a bonus month and a heavy-spend month stay linked.
  • Paths. N_PATHS = 2000 simulated futures, SEED = 20240601, horizons 3, 6 or 12 months. Bands are empirical P10 / P50 / P90.

Risk (<code>plan/risk.py</code>)

  • Cash on each path = starting cash + cumulative (income - essential - discretionary) - debt minimums.
  • Shortfall probability for a month = share of the 2,000 paths where cash is below the reserve (default: median essential spend over the window).
  • Level low / moderate / high compares that probability with your tolerance. Severity (how deep the shortfall goes) and ranked factors are computed from the same paths. Explanatory sentences are templated from the numbers, not generated by an LLM.

Scenarios (<code>plan/compare.py</code>)

Four fixed monthly schedules (do nothing, cut discretionary, pay extra on debt, save extra) are replayed over the same 2,000 paths, so differences are policy effects and not simulation noise. Cash arithmetic reuses the planner's DebtBook, so "cash" has one definition across the app. A recommendation block states the trade-offs.

Accuracy (<code>plan/accuracy.py</code>)

  • No leakage: every forecast origin refits on months strictly before it; the window is tuned on validation; test months are only used for scoring.
  • Baselines: historical average and recurring-payment forecasts. Point error (MAE) and interval coverage/width are compared.
  • Calibration: predicted shortfall probabilities are binned and compared with how often shortfalls actually happened.

Data and stack

Real datayour monthly flows, needs at least MIN_MONTHS = 4
Synthetic data48 months, 3 profiles, shown with a disclosure banner
Stacknumpy, pandas, Pydantic; Recharts on the frontend
EndpointGET /api/forecast-risk/{user} with horizon, sims, seed, profile

Why a bootstrap and not ARIMA/Prophet? Personal finance gives 6-24 noisy months. A model with many parameters overfits; the median-plus-resampled-residuals approach has one tuned parameter (the window), keeps the real shape of your variability, and is explainable in one sentence.

Tests and limits

19 pytest cases cover determinism, window selection, leakage guard, risk monotonicity and scenario paths. Limits: a long upward trend or a one-off life event is not in the history, so the fan will not anticipate it; the report states assumptions on screen.

Feature 4

Photo prices

Take or choose a photo, and the app says what it looks like and suggests a price. Confirm once and it remembers.

What it does

On /photos, tapping the button first asks camera or upload. The photo is analysed and the result reads "Looks like X" with a price field. Confirming the name and price saves it so next time the same item is priced from your own history.

Pipeline

Figure 3. The order is deliberate: your own history first, then a zero-shot model, then a language model only if needed.

How each stage works

  • Embedding. The image goes through CLIP ViT-B/32 (ONNX via fastembed, CPU) to a 512-dimension unit vector. Models download once (~600 MB).
  • Memory. If the cosine similarity to a photo you saved earlier is at least 0.88, the item is the same thing as before and its price comes from your history.
  • Zero-shot. Otherwise the vector is compared with CLIP text embeddings of "a photo of <catalog prompt>" for each catalog item. Logits are scaled by 100 and passed through a softmax to give confidences. No training happens: the catalog is just text.
  • Confidence gate. Under 0.5 the price is left blank rather than guessed, and the vision LLM (Gemini if a key is set, else NVIDIA NIM) names the item.
  • Price. Your median of the last 5 prices for the item, else the catalog price times a city factor. The result shows the range of your own history.

Datasets

Training setnone: zero-shot CLIP, plus your saved items
Catalogexpenses/catalog.py: item, prompt, aliases, category, INR price prior
MemoryPriceMemoryRow: item, price, embedding
EndpointsPOST /expenses/{u}/snap, /suggest, /teach, GET /items

Why this stack

CLIP gives usable recognition for hundreds of everyday objects without collecting or labelling images. ONNX through fastembed avoids installing PyTorch. Keeping the LLM as the last resort keeps cost, latency and privacy low, and the user's own confirmed prices always outrank any prior.

Limits

Prices are priors, not market quotes. Visually similar items (two bottle sizes) can be confused; that is why the user confirms the name and price once.

Feature 5

Statement and receipt OCR

Photograph a bank statement, passbook or receipt and get transactions, with personal identifiers removed first.

What it does

The Upload document page and the statement flow read a photo or scan, show a redacted preview, and import the parsed rows into the ledger after you confirm.

Pipeline

Figure 4. Redaction is the second step, so nothing downstream ever sees account or identity data.

How it works

  • OCR. RapidOCR (PP-OCR on ONNX) runs on this machine. A Devanagari recogniser is tried first (it also reads Latin letters and digits); if fewer than 3 Devanagari letters are found, the English model is used. Boxes are sorted into reading order and merged into lines by vertical position.
  • Redaction (statement_ocr.redact). Devanagari digits are converted to ASCII; whole lines carrying identity (account holder, customer ID, name, address, branch, nominee, in English, Hindi and Marathi) are dropped; then ordered masks replace email, UPI IDs, PAN, Aadhaar (before account numbers so a 12-digit Aadhaar is not mislabeled), IFSC, phone numbers and long account numbers. The response reports how many of each kind were removed.
  • Parsing. parse_transactions extracts date, narration and debit/credit amounts per line; parse_receipt_txn handles single receipts. Rows are categorised with the same merchant rules as everything else.

Data and stack

Inputimage bytes (PNG/JPEG), Hindi / Marathi / English
Outputplain dicts, then TransactionRow on import
EndpointsPOST /api/ocr/extract/{u} then /import/{u}
Why localbank statements are the most sensitive file a user has; no cloud upload is needed

Limits

OCR quality depends on the photo. Unusual layouts may need the hosted vision model; the preview step lets the user catch errors before import.

Feature 6

FinPilot Pay: the phone payment app

A Google-Pay-style scan-and-pay web app installed on the phone. No real money moves; every payment is booked into the real ledger.

What it does

Open /pay on the phone (USB-connected). You scan any UPI QR (or pick a person, type a UPI ID), enter the amount, choose the account, enter any 4-6 digit PIN, and see a success screen with the UPI transaction id. The same payment appears on the website's dashboard and Transactions page.

Screens

Scanlive camera with Chrome BarcodeDetector; fallbacks: gallery photo, typed UPI ID

How it works

Figure 5. A payment end to end, including how the open dashboard finds out.

  • UPI QR format. upi://pay?pa=<vpa>&pn=<name>&am=<amount>&tn=<note>&cu=INR, parsed by lib/upi.ts. Any real UPI QR can be read; the app only reads it and never contacts a bank.
  • Server. POST /api/pay/{user} validates the VPA with a regex and amount 0 < a <= 100000, categorises the merchant, runs the security review, then writes the transaction, the reduced account balance and the review in one Firestore batch.
  • Merchant QR page. /pay/qr on the laptop renders demo merchants with editable amounts for the phone to scan.

Installable app (PWA)

public/pay.webmanifest declares display: standalone, scope /pay, theme blue and 192/512/maskable icons. The page links it through its own layout.tsx. Installed from Chrome (Install app) it launches without the address bar. adb reverse tcp:3000 tcp:3000 and tcp:8000 tcp:8000 make the phone's localhost reach the laptop, which is also a secure context, so the camera works.

Why a web app, not native

One React codebase, instant updates over the dev server, and a PWA is enough to look and feel like an app for this demo. The trade-off is that it depends on the USB forward being active.

Feature 7

Automatic payment security review

Every phone payment is checked as it happens; heavy or unusual ones appear on the dashboard with the verdict and their impact.

What it does

A payment is heavy when it is at least ₹25,000, or at least ₹5,000 and at least 5 times your median payment. Heavy or non-clean payments store a review that the dashboard shows as a card: verdict badge, the seven checks, four impact tiles, insights, and "It was me" / "I did not make this" buttons.

Decision flow

Figure 6. Pure rules over your own history; no model and no network.

The seven checks

CheckPass whenWarn / fail
Within UPI limitamount <= ₹1,00,000fail above
UPI PIN verifiedalways (PIN entered on device)-
Payee recognisedyou have paid this merchant beforewarn: first payment
Size vs your usualwithin 10x of your medianwarn above 10x
Sufficient balancebalance after is at least one month of essentialswarn below; fail if negative
Daily UPI activityUPI sent today <= ₹1,00,000warn above
Time of day05:00 to 23:00 ISTwarn at night

Verdict: any fail gives suspicious; two or more warns give review; otherwise secure.

Impact analysis

  • Balance before and after, and the payment as a percentage of the balance.
  • Month-to-date spend after the payment versus an average full month ("30% above your usual month").
  • Category spend this month versus its usual, and the share of that category's budget used.
  • Runway: balance after divided by typical monthly essentials.
Example. A ₹1,00,000 payment to a new payee from a ₹42,000 balance fails the balance check and is marked suspicious, with balance after -₹58,000. A ₹12,000 payment to a known merchant with enough balance comes back secure.

Endpoints

EndpointPurpose
GET /api/pay/{u}/reviewsnewest reviews with checks and impact
POST /api/pay/{u}/reviews/{id}/statusconfirmed or reported; reported flags the transaction for review

Why rules, not a model

The user can read exactly why a payment was flagged, behaviour is identical on every run, and it needs no training data. Thresholds are product choices and are shown in each check's detail text.

Feature 8

Phone pairing and live sync

Connect the phone to the account you are signed in with, and see every payment appear in about a second.

The problem it solves

The phone has no login. Without pairing it paid into the demo user, while the website was signed in as a real account, so the two ledgers differed. Pairing makes the phone write to your ledger.

Pairing flow

Figure 7. After the first request from the phone, the website replaces the QR with "Phone connected" and returns to the other connectors.

How it works

  • Code. secrets.token_urlsafe(8) stored in pay_pairs with the user id; valid 30 days. The server accepts it only for the user that minted it (403 otherwise).
  • Phone auth. The phone sends X-Pair-Code; a dependency payer accepts either that or a normal bearer token. The phone stores {u, code} in localStorage so the installed app remembers the account.
  • Live sync. LiveSync (mounted in the app layout) polls /api/pay/{u}/live every 1 second, only while the tab is visible. The server returns a global write counter; when it changes, the API cache is cleared and DATA_CHANGED_EVENT makes every mounted useAsync refetch. A toast announces new heavy payments.
  • Phone history. The home screen polls /history every 4 seconds from the same ledger.

The Connect page has a Phone payments tile next to Google Pay and Sheets; the dashboard has the same pairing card.

Why polling, not websockets

A one-line counter endpoint is cheap, works through any proxy and needs no connection state. A websocket or Firestore listener is the upgrade path if many users poll at once.

Limits

The pairing link points at localhost:3000, so it only works while the USB forward is active. Pairing a different account means pairing again from that account's session.

Feature 9

Read cache with write-through

Why the Transactions page used to take forever after a payment, and how it stays fast now.

The problem

A cold Firestore read of one account's 281 transactions took about 14 seconds. The old cache dropped every cached read after any write, so each phone payment sent the dashboard and Transactions page back to cold reads for several queries.

How it works now

Figure 8. Per-table versions and write-through.

  • Each table has its own version number. A write bumps only its table.
  • put() commits to Firestore, then patches the still-current cached query results with the new rows (a row is added to a cached query only if it matches that query's filters), so the next read is warm and already contains the payment.
  • A 45 second TTL still covers writes from other processes. Log-like tables (audit, copilot insights) are never cached.
  • A separate global counter, bumped on every non-log write, feeds the live-sync endpoint.

Verification

Five tests in tests/test_read_cache.py: writes visible immediately, cached rows are copies, repeat reads never touch Firestore, log tables are live, and the new write-through test (no refetch after put, filters respected).

Limits

The first read after a backend restart is still cold. Firestore batches are atomic within 500 rows, not across batches.

Security, privacy and data integrity

What protects the user, and what a reviewer can verify.

Testing, running it, and known limits

Verification done

  • Backend: 19 Forecast & Risk tests and 5 read-cache tests pass (python -m pytest --noconftest tests/test_forecast_risk.py tests/test_read_cache.py).
  • Frontend: tsc --noEmit and eslint clean on the touched files.
  • Manually: heavy payment review verified by API call; pairing claim verified by API (claimed false, then true after first phone request); phone layout checked by screenshots over adb.

Run it

cd backend  && python -m uvicorn app.main:app --port 8000
cd frontend && npm run dev            # http://localhost:3000
adb reverse tcp:3000 tcp:3000 && adb reverse tcp:8000 tcp:8000
phone Chrome: http://localhost:3000/pay   (Install app for full screen)

Known limits

  • No backend tests yet for the payment review rules and the pay/pairing endpoints (verified manually and by API calls).
  • Dashboard live refresh only runs while the tab is visible; the USB forward drops on unplug.
  • Test payments created during development remain in the demo ledger until removed.
  • Two different signed-in accounts see two different ledgers; pair the phone from the account you are viewing.
  • Backend reload on Windows is unreliable; restart uvicorn after backend edits.
